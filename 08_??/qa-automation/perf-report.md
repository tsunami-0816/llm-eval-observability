## 3. M2 入库对账

- 请求侧写入条数 = 51590 + 51750 + 54840 = **158180**；ClickHouse 实收 **158180**（`SELECT count() WHERE model='perf-bench'`）。
- **入库成功率 100%**（HTTP 0 错误 + 条数完全一致），吞吐 545.7 QPS（请求）/ 5456.8 条/s，远超 M2 目标（≥100 QPS、成功率 ≥99.9%）。
- 对账完成后 perf 数据已清理，基线恢复 0 行。

## 4. 瓶颈分析

1. **TPS 拐点**：读/写 TPS 在 10→50 并发间从 491 → 516 / 515 → 546，仅 +5%/+6%，**拐点出现在 ~10 并发**；之后并发 ×5 但 TPS 基本不涨。
2. **拐点后形态**：RT 随并发近似线性上升（读 20→39→97ms；写 19→39→91ms），TPS 平台化 —— 典型「 worker 饱和」形态。
3. **瓶颈定位**：**uvicorn 单进程单事件循环的 CPU/调度上限**。证据：① 读写两条路径（一个走 Redis 缓存、一个只进内存 buffer）TPS 天花板几乎相同（~520），说明瓶颈不在下游 Redis/CH；② CH 聚合在 100 万行下 P95 仅 63.3ms（见基线指标验证表 M3），远非瓶颈；③ 写路径入库对账 100%，flush 协程无掉队。
4. **调优建议**（具体到配置项）：
   - 直接收益最大：`uvicorn --workers 4`（多进程，本机 4~8 核可将天花板近似线性抬升；注意 traces 内存 buffer 每进程独立，flush 批量会变小，可接受）。
   - 备选：`--loop uvloop`（Linux 部署时；Windows 不支持，生产容器内有效）。
   - 下游预留：ClickHouse `max_memory_usage` 已在 docker-compose 限 1G，100 万行聚合充足；若升到千万级再考虑物化视图（基线风险表已登记）。
   - MySQL 连接池（SQLAlchemy 默认 pool_size=5）在跑批+看板并发时富余（Q-001 已实证全 API 最差 31ms），暂不动。

## 5. 结论

读/写接口在 50 并发内 0 错误、P95 < 140ms，M2/M7-API 大幅达标；当前天花板是 uvicorn 单进程，调优路径明确（workers 多进程）。
