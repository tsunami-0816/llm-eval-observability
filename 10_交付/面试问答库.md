## ① 选型对比

### Q1. 明细聚合为什么用 ClickHouse，而不是 MySQL 或 Elasticsearch？

**30 秒版**：明细是「每次 LLM 调用一条」，量大、只追加、查询全是按时间窗做聚合（count / 分位 / sum）。MySQL 行存要做百万级 `quantile`，索引帮不上聚合；ES 能聚合但要 JVM 堆，本机 16G 内存跑不动。ClickHouse 列存 + 向量化，1G 内存上限就能把 100 万条 P95 压到 63.3ms。

- **追问 1（问：为什么不全放 ClickHouse，还要 MySQL？）**：配置类数据（prompt 版本、评测集、run 状态）要改要删、要事务、要唯一性约束，ClickHouse 的 `ALTER UPDATE/DELETE` 是异步 mutation，不适合当业务库。所以「明细进 CH、配置与评测进 MySQL」。
- **追问 2（问：这个量级 MySQL 加索引真不行？）**：百万级 `quantile(latency_ms)` 属于全表扫描式聚合，B+Tree 索引只能定位行、不能帮分位计算；实测同规模在 CH 上 P95 63.3ms，MySQL 没做过对比压测——**这是我没实测的部分**。
- **追问 3（问：ClickHouse 写入会不会成瓶颈？）**：压测 545.7 QPS 时对账 158180==158180，没有丢；但写入路径是单进程 uvicorn + 批量 insert，天花板约 520 TPS，再往上要加写入端或改用 `Buffer` 表。
- **答不上来时的诚实说法**：「ES 我只了解倒排和聚合原理，没在这个项目里实测过对比数据，选 CH 主要是内存约束 + 聚合场景匹配。」

### Q2. 为什么架构评审时砍掉了 Qdrant 向量库、RabbitMQ 和 Go？

**30 秒版**：三条都砍在「本机跑不动 / 性价比低」。Qdrant 容器能起，但相似 case 检索要做 embedding + 召回评测，等于再开一个项目；RabbitMQ 要额外一个容器和运维面，用 FastAPI BackgroundTasks 就能满足 MVP；Go 写入接口同理，多一个技术栈换不来收益，直接 Python 实现。

- **追问 1（问：砍了 Qdrant，RAG 的相似检索怎么讲？）**：本项目没做 RAG 检索，只做 trace 观测与评测。我诚实标注为「未用」，不把容器当能力。
- **追问 2（问：没有 MQ，评测任务可靠性怎么办？）**：这是已知短板——BackgroundTasks 在进程内，重启即丢、无重试、无并发上限。下版本换持久化队列（见 Q7）。
- **追问 3（问：砍功能是不是说明架构能力不足？）**：评审阶段就把「做不完的」显式写进设计书 §8 主动砍掉清单，并在 `_项目状态.md` 标注降级原因，避免"纸面技能点"。这是我刻意练的取舍。
- **答不上来时的诚实说法**：「Qdrant 我只在别的项目里起过容器，没做过召回评测，所以不敢写进简历。」

### Q3. SDK 为什么自研装饰器 + patch，而不用 OpenTelemetry 或 LangChain callback？

**30 秒版**：目标是「接入零改造」。OpenTelemetry 要引 SDK + exporter + collector，本机又多一个进程；LangChain callback 只覆盖 LangChain，覆盖不到裸 openai 调用。自研方案是 `@trace_call` 装饰器 + patch `Completions.create`，业务侧只调一次 `init_tracer`，上报走 fire-and-forget，实测上报故障时业务只劣化 0.926ms。

- **追问 1（问：patch 三方库不稳定怎么办？）**：踩过——第一次 patch `OpenAI.chat` 直接崩（Q-002）。改成 patch `Completions.create`，并用全链路 try/except 兜底：hook 失败就降级到手动装饰器模式，不影响业务。
- **追问 2（问：为什么不用 OTel 的 span 模型？）**：本项目 trace 字段是业务语义（prompt/output/token/cost），不是通用 span 属性；OTel 那套要写 attribute 映射，MVP 阶段收益不如直接定义表结构。但生产化我会选 OTel 做标准层。
- **追问 3（问：多框架怎么覆盖？）**：当前只对 openai 做了真实 hook（实测 `patched=True`），deepseek/langchain 是字段适配上报，不是真实框架拦截——这是能力边界。
- **答不上来时的诚实说法**：「LangChain 的真实 callback 链路我没跑通，只做了字段层适配，简历里标的是『了解』。」

## ② 最难的问题（真实踩坑）

### Q4. 跑批期间所有 API 延迟突然变成 2 秒，怎么定位的？（Q-001，P1）

**30 秒版**：现象是 303 条 case 跑批时，`GET /prompts` 六次实测全是 2049~2070ms，且 run 防重的 409 失效。我先怀疑是评测循环阻塞事件循环，加了诊断日志后发现 `_run_eval` 全程异步只花 0.528s，根本没阻塞。再用裸 socket、curl、127.0.0.1 直连对比——全部 <50ms，只有走 `localhost` 才固定慢 2 秒。根因是 Windows 上 `localhost` 先解析 IPv6 `::1`，连接被拒后回退 IPv4，每个连接固定 ~2s。改成统一用 127.0.0.1 后，回归 8/8：跑批期间探针最差 31ms，防重 409 恢复。

- **追问 1（问：怎么排除是数据库慢？）**：诊断日志记录了 MySQL 查询与 CH 写入的分段耗时，`_run_eval` 总耗时 0.528s；同时探针请求在服务端日志里 `request start→end` 也是毫秒级，说明慢在客户端连接建立阶段。
- **追问 2（问：那为什么还改了 to_thread？）**：IPv6 是测试口径问题，但同步 CH insert 确实是隐患——大批量写会占住事件循环。所以顺手把 `client.insert` 包进 `asyncio.to_thread`，属于防御性加固，不改变根因结论。
- **追问 3（问：怎么防回归？）**：测试脚本统一 127.0.0.1 写进规范；回归用例跑批期间并发探针，把「最差延迟」作为断言口径；这条也写进了 `docs/个人项目不可实现清单.md`（Windows 本机测试坑）。
- **答不上来时的诚实说法**：「第一次我判断错了，认为是后端阻塞，是诊断日志把我拉回来的——这点我在复盘里如实记了。」

### Q5. `init_tracer` 一调用就崩，AttributeError，怎么修的？（Q-002，P1）

**30 秒版**：装了 openai 的环境里 `init_tracer` 直接 `AttributeError: type object 'OpenAI' has no attribute 'chat'`，SDK 完全不可用。根因是我把 `OpenAI.chat` 当类属性 patch，但 openai 1.57.4 里 `chat` 是**实例属性**，`patch.object(OpenAI, "chat")` 必然失败。改成 patch 实测存在的类方法 `Completions.create`，并加全链路 try/except：hook 装不上就降级手动装饰器模式。回归验证 `patched=True`、上报入 CH、断网 2.3s 业务不阻塞。

- **追问 1（问：还有第二个坑？）**：有。hook 是同步函数，里面 `asyncio.create_task` 在没有 running loop 的上下文会 `RuntimeError`，直接把异常抛回业务调用，违反 M8。改成「有 loop 就 create_task，没有就起 daemon 线程用 `asyncio.run` 发送」。
- **追问 2（问：怎么确认 hook 真生效了，不是假 patched？）**：回归里让被 hook 的 openai 调用抛 `APITimeoutError`，确认异常正常抛出且 error trace 成功上报——说明包装层在链路里，不是空跑。
- **追问 3（问：三方库版本漂移怎么办？）**：requirements 把 openai pin 在 1.57.4；hook 目标选「实测存在的类方法」，并在 `docs/个人项目不可实现清单.md` 记了「别 patch 类属性」这条通用教训。
- **答不上来时的诚实说法**：「这类 monkey patch 天生脆，生产我会用官方 callback 或 OTel，不用 patch。」

### Q6. 渗透测试发现整个平台没有鉴权，怎么补的？（Q-009，P1）

**30 秒版**：8.5 安全扫描做渗透时实测：无 key 的 `GET /prompts`、`/datasets`、`/runs`、`/metrics/summary` 全部 200，能读全部 prompt 和聚合数据；无 key `POST /prompts` 直接写库成功。根因是鉴权只在 `traces.py` 里内联写了一份，其他路由从来没挂过。修复是新增 `app/auth.py` 的 `verify_api_key` 依赖，在 `main.py` 对所有业务路由统一 `dependencies=[Depends(...)]`，并设计成 **fail-closed**：key 为空直接全 401。前端 `client.ts` 加拦截器统一带 `X-API-Key`。回归：探针 15/15（无 key 全 401），pytest 62 passed/1 xfailed，浏览器看板正常。

- **追问 1（问：为什么是 fail-closed？）**：config 里 `sdk_api_key` 原本有公开默认值，缺 `.env` 时会静默用弱配置启动（Q-011）。改成默认空串、空即拒绝，避免"配置漏了就裸奔"。
- **追问 2（问：CORS 顺手改了什么？）**：原来是 `allow_origins=["*"]` + `allow_credentials=True` 的危险组合，收紧成 localhost/127.0.0.1 的 5179/5173 四个源、`credentials=False`（Q-010）。
- **追问 3（问：现在还有越权吗？）**：有，且是已知项：单租户设计，改 `project_id` 能横向读别的项目数据（A8 实测 200），按 P3 deferred 留到下版本做项目级授权。
- **答不上来时的诚实说法**：「现在的鉴权是单 key 全站通行，不是多租户权限模型，这是明确的能力缺口。」

## ③ 再做一次（架构级改进）

### Q7. 评测任务现在用 BackgroundTasks，重做会怎么改？

**30 秒版**：改成「持久化任务表 + 独立 worker」。现在 `create_run` 只把 `_run_eval` 塞进进程内 BackgroundTasks：进程重启任务就丢、失败无重试、并发无上限、多实例部署会重复执行。重做方案是把 run 落库（已有 `eval_run.status`），worker 用 Redis 队列或独立进程消费，按 `run_id` 加分布式锁幂等，失败重试带指数退避，进度回写 `total_cases` 与已完成数。

- **追问 1（问：为什么不是直接上 RabbitMQ？）**：本机内存约束下多一个中间件不划算；Redis 已在项目里（做指标缓存），先用 `BRPOP` 队列够用，量上来再换 MQ。
- **追问 2（问：幂等怎么做？）**：`eval_result` 以 `(run_id, case_id)` 为业务唯一键，重跑先删后写或用 upsert；`eval_run.status` 做状态机 `running→done/failed`，只允许单向流转。
- **追问 3（问：进度和取消怎么支持？）**：`eval_run` 增加 `done_cases` 字段按批回写，取消用一个 `cancel_requested` 标记，worker 每处理一批检查一次。
- **答不上来时的诚实说法**：「这套队列方案我只有设计，没实现——项目里跑的是 BackgroundTasks，简历里我也没写"异步任务队列"。」

### Q8. 权限模型重做会怎么设计？

**30 秒版**：把「单 key 全站通行」下沉成项目级授权。现在所有路由只校验 key 是否存在，不校验这个 key 属于哪个 project。重做：`project` 表已有 `api_key`，请求进来先解析出 `project_id`，所有查询强制带 `project_id` 过滤（行级隔离），写入时忽略客户端传的 `project_id`、以 key 解析结果为准；key 比较改 `hmac.compare_digest` 防时序，强制 HTTPS。

- **追问 1（问：怎么防"改 project_id 越权"？）**：关键是**不信任入参**——`project_id` 只从 key 解析，路由层注入到依赖里，SQL 一律 `where project_id = :ctx_project_id`；这就是现在 A8 能越权的原因（入参直接用了）。
- **追问 2（问：要不要 RBAC？）**：单人项目 MVP 只做「项目级隔离」；角色权限（谁能改 prompt、谁能跑评测）等有多人协作需求再加。
- **追问 3（问：key 泄露怎么办？）**：`project.api_key` 支持轮换（新增 `api_key_prev` 双 key 过渡期），并记录最后使用时间；生产加审计日志。
- **答不上来时的诚实说法**：「现在连 HTTPS 都没有，key 是明文 HTTP 头传的，这条我标了 P3 留档。」

## ④ 细节深挖

### Q9. MySQL 和 ClickHouse 双写，一致性怎么保证？

**30 秒版**：`_run_eval` 里评测结果写 MySQL `eval_result`，同时把 trace 批量写 ClickHouse `trace_records`，最后 `db.commit()`。两端顺序是「先攒 CH 行，批量 insert，再提交 MySQL」，CH 失败只打警告不阻塞（观测数据允许最终一致），MySQL 是评测结果的权威源。验收时用 L3 用例做了双写对账，条数与内容一致。

- **追问 1（问：CH 写失败但 MySQL 提交了，不就丢观测数据？）**：会，当前是"丢观测不丢结果"的取舍，属于可接受降级；要严格一致得加 outbox 表 + 重试，这是下版本。
- **追问 2（问：为什么不放在一个事务里？）**：ClickHouse 不支持跨库事务，MySQL 事务管不到 CH；只能靠业务层补偿。
- **追问 3（问：怎么验证真的对上了？）**：L3 集成用例按 run_id 查两边条数比对；性能侧则是 158180 条请求 vs CH 158180 条入库的全量对账。
- **答不上来时的诚实说法**：「严格说是最终一致 + 单向补偿，不是强一致。」

### Q10. X-API-Key 的校验链路是怎样的？能越权到什么程度？

**30 秒版**：`main.py` 对业务路由统一挂 `Depends(verify_api_key)` → `app/auth.py` 从 `X-API-Key` 头取值，和 `settings.sdk_api_key` 比对，不匹配抛 401，key 配置为空则全拒绝（fail-closed）。能越权的点：单 key 单租户，改请求里的 `project_id` 可读到其他项目的数据；key 明文走 HTTP，远程部署可被嗅探；比较用 `!=` 有时序攻击面。

- **追问 1（问：为什么不在每个路由里各写一遍？）**：我第一版就是内联在 `traces.py`，结果其他路由全裸奔（Q-009）。统一依赖的好处是"新增路由默认带鉴权"，漏挂会被渗透用例打出来。
- **追问 2（问：SDK 上报端和前端用的是同一个 key？）**：是同一个 `settings.sdk_api_key`，MVP 简化；生产应该分「写入 key」和「管理 key」两套。
- **追问 3（问：401 和 403 怎么区分？）**：当前只有 401（未带/带错 key）；没有"带对 key 但无权访问该资源"的场景，因为还没做项目级授权。
- **答不上来时的诚实说法**：「没有 RBAC，没有租户隔离，这是 P3 明确留档的缺口。」

### Q11. 百万条聚合 63.3ms 是怎么做到的？缓存起多大作用？

**30 秒版**：两条——①存的是列式明细表 `trace_records`，`summary` 只算 count/sum/quantile/时间窗过滤，CH 向量化执行；②`metrics` 接口套了 30 秒 Redis 缓存装饰器，缓存挂了 fail-open 不阻塞。压测时特意**清缓存**再打 30 次取 P95，所以 63.3ms 是冷查询口径，不是缓存命中。

- **追问 1（问：缓存 key 怎么设计的？）**：`cache:{函数名}:{args}:{kwargs}`，参数进 key，所以不同 `range_days` 不会串；TTL 固定 30s，容忍 30s 内的数据延迟。
- **追问 2（问：有没有用物化视图或预聚合？）**：**没有**，就是实时 SQL 聚合。百万级够用，更大规模才需要物化视图或按小时预聚合表。
- **追问 3（问：timeseries 的 metric 参数呢？）**：这是我留下的缺陷——`metric` 形参接收后没用，SQL 写死 `quantile(latency_ms)`，所以 `metric=cost` 和 `metric=latency` 返回一样（Q-006，P3，用 xfail 用例标记）。
- **答不上来时的诚实说法**：「预聚合和物化视图我没做过，只做了实时聚合 + 短 TTL 缓存。」

### Q12. 上报是异步的，断网/超时怎么保证不拖累业务？

**30 秒版**：`send_trace` 是 fire-and-forget：有 running loop 就 `create_task`，同步上下文（比如被 hook 的同步 openai 调用）就起 daemon 线程 `asyncio.run` 发送。aiohttp 设 2s 总超时，所有异常在 `_post` 里被吞掉、只打 debug 日志。实测上报端不可达时，业务侧平均只劣化 0.926ms/次。

- **追问 1（问：为什么不用 asyncio.create_task 一把梭？）**：同步上下文没有 running loop，`create_task` 抛 `RuntimeError` 会反噬业务调用——这是 Q-002 的第二个坑，必须有 daemon 线程兜底。
- **追问 2（问：fire-and-forget 会不会丢数据？）**：会。进程退出时队列里的 trace 可能丢，且没有本地缓冲/重试。生产要加本地 spool + 批量重发。
- **追问 3（问：为什么超时设 2s？）**：要小于业务可容忍劣化，同时给正常上报留余量；这个值是经验值，没做过延迟分布压测。
- **答不上来时的诚实说法**：「0.926ms 是"端不可达"的劣化实测，不是"高延迟"场景，后者没测。」

## 五、使用提示

- 数字口径与 `10_交付/简历项目描述.md` 的「数据出处映射表」保持一致；面试前只看那一张表即可。
- 被问到「评测准确率 / 效果提升多少」时，直接说：判官是 Mock，**只有链路和性能数据，没有效果数据**。
- 被问到「团队协作 / 主导」时，如实说单人开发 + AI 协作，重点讲取舍与踩坑定位过程。
