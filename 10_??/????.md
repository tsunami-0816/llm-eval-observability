## 二、上线方案

### 2.1 部署步骤

```powershell
# 1. 中间件（MySQL 3310 / Redis 6381 复用共享容器；ClickHouse 本项目容器）
docker compose -f 05_代码/docker-compose.yml up -d eoe-clickhouse

# 2. 配置
cp 05_代码/backend/.env.example 05_代码/backend/.env   # 按需改密码与 key

# 3. 后端
cd 05_代码/backend
pip install -r requirements.txt
python init_db.py                                     # 建 MySQL 5 表 + CH trace_records
python -m uvicorn app.main:app --host 0.0.0.0 --port 8086   # 生产加 --workers 4（见 perf 报告）

# 4. 前端
cd 05_代码/frontend
npm install
npx vite build                                        # 注意：用 vite build，非 npm run build（Q-016）
npx vite preview --port 5179                          # 或 nginx 托管 dist/

# 5. SDK（业务方接入）
pip install ./05_代码/sdk
```

### 2.2 环境变量清单（.env.example 全表）

| 变量 | 说明 | 生产要求 |
|---|---|---|
| APP_HOST/APP_PORT/APP_ENV | 监听与运行环境 | APP_ENV=prod 时建议关 docs（Q-012） |
| MYSQL_HOST/PORT/USER/PASSWORD/DB | 业务库（共用 3310） | 强密码，库 eoe |
| CLICKHOUSE_HOST/HTTP_PORT/USER/PASSWORD | 明细库（8123） | 设密码（本地实测空密码 403 已拦外部） |
| REDIS_HOST/PORT/DB | 缓存（共用 6381，本项目 DB=3） | requirepass（Q-014） |
| SDK_API_KEY | 上报与全接口鉴权 key | 必改默认值；远程必须 HTTPS（Q-015） |
| OPENAI_API_KEY/BASE_URL/MODEL | 评测用 LLM | 不配则走 mock（M6 未验证项） |

### 2.3 数据库初始化

- 脚本：`backend/init_db.py`（幂等）——MySQL：`project` / `prompt_version` / `eval_dataset` / `eval_case` / `eval_run` 五表（utf8mb4）；ClickHouse：`trace_records`（按天分区）。
- 最小种子：2 prompt + 1 数据集 + 3 case（重置脚本同款，见 `07_联调/数据重置记录.md`）。

### 2.4 回滚方案

1. **代码回滚**：Git tag 交付版本（`v1.0.0`），回滚 = `git checkout v1.0.0` + 重启 uvicorn / 重发前端 dist。
2. **数据回滚**：MySQL `mysqldump --default-character-set=utf8mb4 eoe > backup.sql`；CH `clickhouse-client --query "SELECT * FROM trace_records FORMAT Native" > ch_backup.native`。本项目无破坏性 schema 变更，回滚无需迁移脚本。
3. **依赖回滚**：requirements 全 pin，旧版本环境用 `pip install -r requirements.txt --force-reinstall` 重建。
4. 回滚验证：`/health` 200 + P0 冒烟 15 用例（`08_测试/qa-automation/data/p0_cases.json`）。

### 3.4 选题准确率复盘（step00 回头对账）

**a) 工作量预估**：设计书**缺 §6 工作量拆解（人天×模块）**——上一个项目（saas-workflow-agent）step10 已回填「设计书必须含 §6/§7/§8」，本项目设计书仍未包含，回填要求无机器闸门形同虚设（→ 改进建议 #55）。仅有基线口径 ≤12 人天；实际 2026-10-30 单日完成全流程（AI 全程协作，用户卡点 4 次约半小时）。**「人天」口径在 AI 协作下彻底失真**，建议 step00 估算改记「步骤轮次/卡点次数」或显式标注 AI 协作系数（→ 改进建议 #57）。

**b) 技术选型翻车 vs 顺利**：

| 选型 | 预判 | 实际 | 结论 |
|---|---|---|---|
| openai SDK hook | 常规集成 | **翻车**：`OpenAI.chat` 类属性不存在（版本漂移），P1 事故 1 次 | 进避坑清单 |
| PowerShell 提交中文 | 工具细节 | **翻车**：`curl` 别名按 Latin-1 吞中文（Q-004） | 文档提示 curl.exe/python |
| vite dev server | 常规 | 小坑：Windows 默认 IPv6（老坑重现，冒烟 1 轮修掉） | host:true 写进模板 |
| ClickHouse | 担心 1M 聚合超 1s | **超预期**：P95 63.3ms，灌 100 万 13s | 物化视图预案未启用 |
| FastAPI 异步 + CH 批量插入 | 担心 100 QPS | **超预期**：545.7 QPS 0 错误 | Go 边车确认不需要 |
| Vue3 + Element Plus | 常规 | 零返工 | — |

**c) 硬骨头模块**：设计书未写硬骨头（三节缺失）。事实硬骨头：①SDK 自动注入——真硬（1 次 P1）；②高并发写入——不硬（内存 buffer + CH 批量一次过）。无「做不出来被迫降级」的模块（Qdrant/RabbitMQ/Go 是 step1 主动降级，非做不出）。

**d) JD 对账覆盖率**（原表 18 行全 ✅/◐，逐项复核实际落地）：

| 实际落地档 | 行数 | 明细 |
|---|---|---|
| 真实落地 | 13 | FastAPI/Agent 观测/Prompt 评测/评估体系/LLM 监控/评测 API/性能优化/MySQL/Redis/ClickHouse/自动化测试/Vue3+TS/问题排查 |

**教训**：对账表标的是「规划覆盖」不是「实际落地」——面试按原表讲会穿帮 2 处（Qdrant/RabbitMQ）。对账表必须加「step10 落地验证」列（→ 改进建议 #57）。
